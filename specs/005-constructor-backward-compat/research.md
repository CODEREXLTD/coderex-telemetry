# Research: Constructor Backward Compatibility

**Feature Branch**: `005-constructor-backward-compat`  
**Date**: 2026-04-02

## R-001: PHP Constructor Overloading Pattern (PHP 7.4+)

**Decision**: Use type inspection via `is_array()` on the first argument.

**Rationale**: PHP 7.4 has no native method overloading. The spec (FR-004) mandates detection based on the first argument's type. Checking `is_array($firstArg)` is clean, readable, and the standard PHP idiom for dual-signature constructors. No need for `func_get_args()` fragility.

**Alternatives considered**:
- `func_get_args()` — works but is less type-safe and harder to document. Rejected for lower readability.
- Union type `array|string` first parameter — requires PHP 8.0+. Rejected because project targets PHP >=7.4.

**Implementation approach**:
```php
public function __construct($configOrApiKey, string $apiSecret = '', string $pluginName = '', string $pluginFile = '')
{
    if (is_array($configOrApiKey)) {
        $config = $configOrApiKey;
    } elseif (is_string($configOrApiKey)) {
        // Legacy 4-param path — build config array from positional params
        trigger_error('...deprecation message...', E_USER_DEPRECATED);
        $config = self::buildLegacyConfig($configOrApiKey, $apiSecret, $pluginName, $pluginFile);
    } else {
        throw new InvalidArgumentException('...');
    }
    // ... proceed with existing array-based initialization
}
```

## R-002: Slug Derivation via `sanitize_title()`

**Decision**: Use `sanitize_title()` when available, with an inline fallback for non-WordPress contexts (testing).

**Rationale**: The spec (FR-003) requires slug derivation via `sanitize_title()` (e.g., `"My Plugin"` → `"my-plugin"`). This is a WordPress core function and will always be available at plugin initialization time in production. However, the test suite runs without WordPress — `tests/bootstrap.php` stubs many WordPress functions but does NOT currently stub `sanitize_title()`.

**Alternatives considered**:
- Always use a custom slug function — rejected because the spec explicitly requires `sanitize_title()`.
- Add `sanitize_title()` as a utility in `src/Helpers/Utils.php` — rejected; the WordPress function is the canonical implementation and we only need a test stub.

**Action items**:
- Add a `sanitize_title()` stub to `tests/bootstrap.php` with a simplified implementation: `strtolower(preg_replace('/[^a-z0-9\-_]/i', '', preg_replace('/\s+/', '-', $title)))`.

## R-003: Old Constructor Field Mapping

**Decision**: Map positional params to the internal config array with these exact semantics.

**Rationale**: Based on the spec (FR-002, FR-003, FR-007) and current code analysis:

| Positional Param | Config Key | Value |
|---|---|---|
| `$apiKey` | `apiKey` | Passed directly |
| `$apiSecret` | `apiSecret` | Passed directly |
| `$pluginName` | `pluginName` | Passed directly |
| `$pluginFile` | `pluginFile` | Passed directly |
| *(derived)* | `slug` | `sanitize_title($pluginName)` |
| *(derived)* | `version` | Auto-detected via `Utils::getPluginVersion($pluginFile)` |
| *(derived)* | `driver` | `'open_panel'` (hardcoded default) |
| *(derived)* | `unique_id` | Auto-generated by `get_or_create_unique_id()` (existing logic) |

**Validation for legacy path** (FR-005):
- Exactly 4 positional params must be provided (first must be string).
- `$apiKey` must not be empty.
- `$pluginFile` must not be empty.
- Wrong param count (3, 5, etc.) → `InvalidArgumentException`.

## R-004: Testing `trigger_error(E_USER_DEPRECATED)` in PHPUnit 9.5

**Decision**: Use PHPUnit 9.5's built-in `$this->expectDeprecation()` and `$this->expectDeprecationMessage()`.

**Rationale**: PHPUnit 9.5 has native support for asserting deprecation notices triggered by `trigger_error($msg, E_USER_DEPRECATED)`. No custom error handler or mocking is needed.

**Test pattern**:
```php
public function testLegacyConstructorEmitsDeprecation(): void
{
    $this->expectDeprecation();
    $this->expectDeprecationMessage('Passing positional parameters to');
    new Client('api-key', 'secret', 'My Plugin', '/path/plugin.php');
}
```

**Alternatives considered**:
- Custom `set_error_handler()` in test — works but unnecessarily complex when PHPUnit already supports this.

## R-005: Validation Boundary — Current vs Legacy Constructor

**Decision**: Both paths converge to the same internal validation after config normalization.

**Rationale**: The current array constructor requires `pluginFile` and `slug`. The legacy path derives `slug` from `pluginName`, so it only needs to validate that `pluginFile` and `pluginName` (and `apiKey`) are non-empty. After building the config array from positional params, the existing validation flow handles the rest.

**Flow**:
1. Legacy path: validate positional params → build config array → fall through to existing array validation
2. Array path: unchanged — existing validation continues as-is
3. Invalid first-arg type: throw `InvalidArgumentException` immediately
